# 记账本 App —— 竞品逻辑研究与设计参考

> 调研时间：2026-11。目的：为我们自己的家庭记账本（Cloudflare 全家桶 + PWA）确定产品逻辑。
> 调研对象：一木记账、趣记账、鲨鱼记账、随手记、Lumio（情侣账）等。
> 注意：下述功能描述来自各产品公开文档/商店页，仅作逻辑参考，具体以产品实际版本为准。

---

## 一、市面上的多人共享，其实只有四种模型

这是最关键的认知。所有记账 App 的"多人"都落在这四种里，差别只是包装。

| 模型 | 代表 | 共享什么 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **① 共用账号** | 一木记账「共用账号」 | **全部数据**：账单、分类、账户、标签 | 零开发成本，什么都能共享 | 分不清谁记的；两人会互相覆盖；无法分别统计 |
| **② 共享账本** | 一木记账「共享账本」 | **只有账单**，分类/账户/标签各用各的 | 边界清晰，成员可退出、可被移除 | 分类不统一，统计口径会乱 |
| **③ 聊天式群账本** | 趣记账 | 一个"群"里所有人的流水 | 有"谁在什么时候记了什么"的社交感，实时推送 | 重，消息噪音多，适合旅行/宿舍/班委 |
| **④ 双人合并视图** | Lumio（情侣）等 | 各自私人账 + 一个"共同"部分 | 保留个人隐私，又能看合计 | 需要设计"哪笔算共同"的判定 |

### 一木记账的做法（原文要点）

> - 共享账本：**仅账单**，不共享账户、分类、标签；各自使用自己的账号
> - 共用账号：**全部数据**；多台设备登录同一账号
> - 共享方式：账本成员页生成**邀请二维码，10 分钟内有效**
> - 成员管理：创建者可移除成员，成员可主动退出
> - 可**按成员筛选**账单
> - 系统账本「日常账本」**不能共享**，要新建账本再共享，老账单可批量迁移

来源：<https://www.yimuapp.com/doc/function/duo-ren-ji-zhang.html>

**可以直接抄的三点**：
1. 系统默认账本不可共享 —— 强制用户显式创建"家庭账本"，避免误操作把私人账晒给家人。
2. 邀请码**短时效**（10 分钟），而不是永久有效，安全得多。
3. 共享内容有**明确边界**（只共享流水），预期不落空。

## 二、用户需求："每个人记自己的，然后能把两个人的合并"

这句话有三种技术实现，差别巨大：

### 方案 1：两个私有账本 + 一个家庭账本，记账时选投给谁
- 用户每次记账要**做一次选择**（记到我的 / 记到家里）
- 缺点：多一步点击，破坏"3 秒记账"；选错要改，容易挫败

### 方案 2：**一条账单只有一个归属，但带"谁记的"**（推荐）
```
entries 表：household_id（哪个账本） + created_by（谁记的）
```
- 记账时**不用选**，默认进当前账本，自动带上"我"
- **个人视图** = `WHERE created_by = 我`
- **家庭视图** = 全部（不筛 created_by）
- 合并 = 换一个查询条件，**不复制数据**

### 方案 3：各自独立账本 + 手动勾选"合并成报告"
- 最灵活，但要把两边的数据结构对齐、还要处理分类不一致
- 适合做"年度报告分享"，不适合做日常主流程

**结论：选方案 2。核心洞察是一句话——**

> **"合并"是一个视图，不是一次数据搬运。**
> 一旦你在数据库里真的复制出"合并后的账单"，就同时拥有了两份会分叉的真相：
> 改一笔要改两处，删一笔可能只删掉一边，统计必然对不上。

这个判断会直接决定我们的表结构，所以放在最前面。

## 三、"3 秒记一笔"到底靠什么（效率设计清单）

记账类产品的生死线不是功能多少，是**记一笔要多久**。鲨鱼记账直接把"3 秒钟快速记账"写进 App 名字，趣记账写"每次记账不要超过 2 秒"。

它们共同的做法：

| 设计点 | 具体做法 | 为什么有效 |
| --- | --- | --- |
| 打开即键盘 | 进首页就是**数字键盘**，不是列表 | 少一次点击 |
| 分类九宫格 | 大图标 + 文字，**最近用过的排前面** | 早餐/通勤这类高频项一次命中 |
| 日期默认今天 | 只有需要补记才点日历 | 90% 的账是当天的 |
| 备注可空 | 不填也能存；输入时**联想历史备注** | 鲨鱼记账专门提"备注智能提示" |
| 保存即反馈 | 存完弹 toast，带**撤销** | 记错了不用进列表找 |
| 断点记忆 | 重开 App 保留上次的分类/草稿 | 趣记账叫"断点记账，总记住最后的输入状态" |
| 日历补记 | 月历上直接点某天补 | 鲨鱼记账"记账日历：查看、补记" |
| 定时记账 | 房租/话费/会员这类**周期性固定支出自动生成** | 否则每月都要手动重复 |

**我们 v1 必须做到的**：打开即键盘、九宫格分类、默认今天、备注联想、保存后可撤销。
**v1 不做**：语音记账、拍照识别小票、多货币、商家/位置/天气、皮肤、AA 分账、预算提醒 —— 这些是成熟产品第 3 年以后加的，早期做只会拖死进度。

## 四、统计视图（比"记账"更影响留存）

各家高度一致，说明就是这个套路：

1. **本月三数**：收入、支出、结余（首页头部，大字）
2. **分类饼图/环形**：花在哪了，点击某一类能下钻到明细
3. **月度趋势折线**：这个月比上个月多花了多少
4. **日历热力**：哪几天花钱凶
5. **搜索 + 多维筛选**：按时间、分类、成员（趣记账支持按"大小分类、商家、项目、成员创建人"汇总）

家庭场景还要加一个：**按成员对比**（我花了多少、TA 花了多少）——这正是方案 2 能免费给出的能力。

## 五、被低估的两个功能：软删除 与 变更历史

趣记账明确写了：
> - 记账详情支持**变更历史的查看**
> - 管理员及成员都可以**查看删除的记账**

多人协作时，账"少了一笔"是最容易吵架的事。做法：

- 删除 = `deleted_at` 打标记（**软删除**），不真删
- 界面上有个"回收站"，能看到谁在什么时候删了什么
- 编辑保留 `updated_at`，重要字段变更记一条 audit

成本极低（一个字段 + 一个页面），但能消灭"谁动了我的账"这类信任问题。

## 六、PWA 与离线的现实约束

趣记账：「无网络时，也可以增加或修改记账，有网络时再自动发送」。
这一点在纯 Web 上比原生难，但可行：

1. Service Worker 缓存页面外壳 + 最近账单 → 没网也能打开
2. 记账写入 IndexedDB 的 **outbox 队列**
3. 联网后按 `client_uuid` 重放，服务端唯一索引保证**幂等**（重复提交不会变成两笔）
4. 冲突策略：以服务端 `updated_at` 为准，或者"最后写入者胜"——家庭场景够用

**不要**在第一版做"离线编辑已同步的旧账"——离线只做"新增"，冲突面最小。

## 七、我们的 v1 范围（砍完之后）

| 模块 | v1 做什么 | 不做 |
| --- | --- | --- |
| 账号 | 注册/登录/登出（方式待定：用户名密码 or 邮箱） | 第三方登录、手机号验证码 |
| 账本 | 一个"家"账本，两人共享 | 多账本、多币种 |
| 记账 | 金额/收支/分类/日期/备注/谁记的 | 分账、AA、转账、债务 |
| 列表 | 按月、按成员筛选，搜索 | 高级多维筛选 |
| 统计 | 本月三数 + 分类饼图 + 按成员对比 | 预算、趋势预测 |
| 其他 | 撤销、软删除回收站 | 变更历史详情、提醒推送 |
| 形态 | 响应式网页 → 后期 PWA | 原生 App |
